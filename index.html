01

跟着一次告警走完循环

从一个可回答的问题开始：20:00 后的订单失败，与哪项变化最相关？每次模型决策都以当时已经取得的证据为输入。

用户输入「订单服务的 500 错误突然增多，帮我调查原因。」
先确定故障范围query_metrics

订单接口的 HTTP 500 比例从 0.2% 升到约 7%，集中在 20:00 之后。

判断依据　错误比例只说明用户受影响。下一步查同一时段的失败日志。

寻找失败请求的共同点query_logs

多条 500 日志都出现“等待数据库连接超时”。

判断依据　等待连接可能由流量突增、慢查询或连接池变小引起。下一步检查最近的变更。

把变化放回时间线上get_deployments

19:56 发布的新配置把连接池上限从 50 降到了 10。

判断依据　配置变更先于错误增长。还需要连接占用率和请求流量来验证因果关系。

区分事实与待验证的假设final response

首要假设是连接池上限降低，导致请求排队超时。记录支持证据，并列出仍需核验的指标。

判断依据　本步没有工具调用，队列也没有待处理输入，本轮调查结束。用户追问会开启新的 Turn。

在这个例子里，模型作出四次决策，工具执行三次。最后一步只生成文字结论，也算一个 Step。

02

Session、Turn、Step 怎么数？

同一段调查可以从三个尺度观察。先确定统计对象，才知道耗时、失败率和模型用量该记在哪里。

Session · 会话
把多轮交互关联到同一份历史。用它还原整次调查，并汇总跨轮用量。
Turn · 一轮处理
驱动器领取待处理输入后开展的一轮工作。适合衡量用户从提问到答复等了多久。若进入首个 Step 前输入被拒，本轮可以有零个 Step。
Step · 一次决策
覆盖一次模型决策及其引发的一批工具调用，也可能没有工具。失败的模型请求可以在同一 Step 内重试，所以精确的请求次数要看请求记录。
03

谁负责推动下一步？

在 DeepSeek Harness（DSH）里，模型提出下一步动作，宿主运行时负责执行、记录和收尾。

组装上下文→请求模型→执行工具→追加结果
↳ 带着更新后的历史进入下一步；无工具调用且无待处理工作时结束本轮。
服务职责与作用
ctx.agents创建或恢复 Agent
让后续追问回到已有的调查。
ctx.agentLoop驱动 Turn 与 Step
决定何时请求模型、执行工具、继续或收尾。
ctx.systemPrompt组装系统指令
结合当前可见工具与提示词，告诉模型有哪些能力可用。
ctx.llm与模型提供方通信
发送派生的消息历史，处理流式文本和工具调用。
ctx.tools解析、校验与执行工具
把调用交给执行器，应用权限策略，返回相关联的结果。
ctx.sessions维护会话与事件
保存输入、响应和工具结果，供下一步派生历史。

把循环缩到一个可以运行的例子

下面的 JavaScript 同时模拟模型和三个只读工具。注意 history.push 的两处写入：先保存模型的决定，再用调用 ID 关联工具结果。真实模型会读取结果内容，自行决定下一步。

JavaScript · 离线教学模型
const evidence = {
  query_metrics: "20:00 后订单接口的 500 比例升高",
  query_logs: "失败请求多次等待数据库连接超时",
  get_deployments: "19:56 发布，连接池上限从 50 改为 10"
};

// 用固定决策代替模型，离线复现四个 Step。
function decide(history) {
  const calls = Object.keys(evidence);
  const seen = history.filter(m => m.role === "tool");
  const name = calls[seen.length];
  if (name) return { id: "call-" + name, name };
  return { text: "候选原因是连接池上限降低；还需核对连接占用与流量。" };
}

function investigate() {
  const history = [{ role: "user", text: "调查订单服务 500" }];
  for (let step = 1; step <= 4; step++) {
    const reply = decide(history);
    history.push({ role: "assistant", ...reply });
    if (!reply.name) return history;
    history.push({ role: "tool", callId: reply.id,
                   text: evidence[reply.name] });
  }
  throw new Error("已达到本次演示的步数上限");
}

console.table(investigate())
无网络请求
接入真实工具时，运行时还要处理什么？
一次响应可能请求多个工具。该版本默认允许同批最多 10 个并发调用，maxParallelToolCalls: 1 可使其串行，要求独占的工具会形成执行屏障。用户取消时，运行时通过信号通知正在工作的组件退出，并保留已送达的文本。工具本身也要响应取消信号。
04
进程退出后，还能恢复什么？
DSH 将已接纳的事实追加到 Session Log，再从事件派生模型使用的消息历史。配置 JSONL 持久化后，重启进程可以重建已经保存的会话。
“没有成功记录”能证明回滚失败吗？
假设外部系统已完成回滚，而 Agent 在写入 tool/result 前崩溃。重放日志能恢复已知历史，此时外部操作的结果仍然未知。先用稳定的 operationId 查询外部状态，再决定是否重试。服务端也应以该 ID 去重，避免重复执行。
05
Native 与 PTC 怎么选？
共同的问题是查一批告警，告诉用户哪些仍在触发。两种方式的区别，主要在于中间结果由谁读取、筛选和汇总。
NATIVE TOOL CALLING
模型看结果，决定后续动作
模型直接看到可用工具及参数结构。一次响应可以提出多个调用，再读取返回的结果。若下一步需要理解一段含糊的日志，这种方式便于模型逐步判断。
PROGRAMMATIC TOOL CALLING
程序处理结果，模型读摘要
模型看到 run_code 和动态生成的 TypeScript SDK。它可用循环、分支和过滤组合工具，只把选出的值交回模型。嵌套调用仍走工具执行与权限流程。


11Native 逐个决策
2Native 一批并发
2PTC 一段程序
数字表示模型请求数。假设 ID 已知、每个告警查一次、全部成功，最后再请求一次模型写总结。逐个决策为 N + 1；另两者各用一次请求发起查询、一次总结。三种方式查询告警的次数均为 N。这是推演，不是性能实测。


TypeScript · PTC 程序体
// run_code 内的示例。假设已注册 get_grafana_alert，
// 其 SDK 返回 { id: string, status: string, service: string }。
const ids = ["A001", "A002", "A003"];
const alerts = await Promise.all(
  ids.map(id => tools.get_grafana_alert({ id }))
);
const firing = alerts
  .filter(alert => alert.status === "firing")
  .map(({ id, service }) => ({ id, service }));
inspect(firing);
若 A001 与 A003 正在触发，inspect 只输出这两条的编号和服务名。原始告警详情留在程序内。若必须逐条阅读详情才能决定下一步，或只查一条告警，生成和执行程序的额外开销也应计入。
在 DSH 中切换执行器
在同时声明这两个插件的基础组合中，把下面片段保存为 ptc.patch.yml。在已完成依赖安装和模型配置的 DSH 源码根目录运行 pnpm dsh web --patch ./ptc.patch.yml。如果 Web Agent 有自己的执行器，选用其 PTC 预设；最近作用域的执行器生效。
YAML · ptc.patch.yml
- id: tool-executor-native
  disabled: true

- id: tool-executor-ptc
  disabled: false
生产环境还应设置工具权限、执行超时和资源预算。
06
观察执行，还是改变执行？
两个插件的挂载点不同。事件监听器能告诉你发生过什么；执行前的 Hook 可以改变一次工具调用的去向。
观察 · 给每条调查轨迹加上序号
在同一 DSH 工作区的插件包中使用下列 TypeScript，声明对应依赖并通过 Cordis 加载。触发一次会用到工具的调查后，按会话 ID 过滤日志，即可看到每轮起止与工具活动。
TypeScript · loop-logger.ts
import type { Context } from '@deepseek-ai/cordis'
import type {} from '@deepseek-ai/dsh-session'

export const name = 'loop-logger'
export const inject = ['sessions']
const tracked = new Set([
  'turn/start', 'step/start', 'tool/call',
  'tool/result', 'step/end', 'turn/end',
])

export function apply(ctx: Context) {
  ctx.on('session/event', (session, event) => {
    if (tracked.has(event.type)) {
      console.log(session.id, event.seq, event.type)
    }
  })
}
例如，同一个会话下出现 tool/call 和 tool/result 两行，即可继续到会话记录中按调用 ID 查看配对详情。这里只打印元数据，保留调试所需线索。
控制 · 为只读调查拒绝回滚
TypeScript · rca-readonly.ts
import type { Context } from '@deepseek-ai/cordis'
import type {} from '@deepseek-ai/dsh-tools'

export const name = 'rca-readonly'
export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.on('tools/pre-execute', async (exec, next) => {
    if (exec.name === 'rollback_deployment') {
      return { kind: 'deny', reason: '本次调查只允许读取证据' }
    }
    return next()
  })
}
查询工具调用 next() 继续交给后续处理器。回滚请求得到带原因的拒绝。此示例只演示命名工具的拦截；强制只读还需要最终的 ctx.tools.guard()、可用工具限制，以及外部服务签发的只读凭据。
需求应该落在哪一层？
增加查询能力，注册 Tool；复用客户端或缓存，提供 Service；记录耗时与失败，监听事件；调整指令，扩展 System Prompt。需要强制按“收集证据 → 验证 → 出报告”推进时，再考虑 Workflow 或自定义 Agent。
